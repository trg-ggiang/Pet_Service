## Environment

Frontend Supabase variables are read from `NEXT_PUBLIC_*` first, with `VITE_*` fallback:

```text
NEXT_PUBLIC_SUPABASE_URL=
NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY=
VITE_SUPABASE_URL=
VITE_SUPABASE_PUBLISHABLE_KEY=
```

## API Access

During local development, Vite proxies `/api` to `http://localhost:5050`.

Role-specific page implementations live under `frontend/src/features/<role>/pages/`. Role-specific API clients that are only used by that role live under `frontend/src/features/<role>/services/`.

The app imports role pages directly from `frontend/src/features/<role>/pages/`. Do not add new page wrappers under `frontend/src/pages/`.

Customer shared API clients live under `frontend/src/services/customer/` because they are also used by shared customer components and types. Admin pages load backend data through `frontend/src/features/admin/services/admin.ts` instead of rendering Figma/sample arrays directly in page state.

Admin dashboard, reports, and settings UI sections live under `frontend/src/components/admin/`; role page files stay as stateful containers that call the admin feature service.

Doctor pages load profile, schedule, medical records, statistics, and exam-screen context through `frontend/src/features/doctor/services/`. Doctor role pages should not render sample patient, record, vaccine, visit history, schedule summary, or report arrays directly from page files.

Staff portal pages load profile, appointments, grooming, boarding, and payment data through `frontend/src/features/staff/services/`. Staff UI sections live under `frontend/src/components/staff/`; role pages should stay as stateful containers and should not render sample appointment, grooming, boarding, or payment arrays.

Auth pages keep page-level state and submit handlers under `frontend/src/features/auth/pages/`, render shared UI from `frontend/src/components/auth/`, and call shared auth API helpers from `frontend/src/services/auth.ts`.

## Refactor Boundaries

- `components/`: reusable UI components only.
- `features/<role>/pages`: page and portal screens grouped by role.
- `features/<role>/services`: role-scoped API clients.
- `services/`: shared API clients and compatibility wrappers.
- `hooks/`: custom React hooks prefixed with `use`.
- `types/`: shared TypeScript types.
- `utils/`: framework-agnostic helpers.
- `constants/`: shared constants and route/config values.
- `contexts/`: global React context/state providers.
- `layouts/`: reusable layout shells.

## Doctor Portal Notes

- `DoctorPortal.tsx` should stay as a thin container for navigation state and service calls.
- Doctor portal, records, stats, and settings UI sections live under `frontend/src/components/doctor/`.
- Schedule rows, status display config, portal header metadata, summary counts, medical-record filtering, stat KPI cards, and settings payloads are returned by the backend; frontend components render those values instead of remapping appointment status labels or rebuilding business-facing rows.

## Auth Notes

- Login, register, splash, welcome, and forgot-password UI sections live under `frontend/src/components/auth/`.
- Auth page files should remain thin containers for local form state, validation, and service callbacks.
- Login and register submit through the backend-backed helpers in `frontend/src/services/auth.ts`; forgot-password currently remains a local mock flow until a reset-password API is added.

## Customer Portal UX Notes

- Customer dashboard cards should keep child content inside their parent panel at desktop and mobile breakpoints.
- Appointment and service-history filter bars should use available horizontal space to avoid sparse layouts.
- Custom dropdown menus are preferred over native selects when option-list styling needs consistent spacing, hover states, and selected indicators.
- Pet profile cover images and avatars should stay compact unless the surrounding layout is explicitly redesigned.
